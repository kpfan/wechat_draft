本次贡献：将现有 Python 原型中的称呼判断和节日祝福写作规则适配到 C# 项目。维护入口集中在一个文件，继续使用原项目的 HTTP 客户端、任务流程和 JSON 协议，无新增依赖或 Agent 框架。

## 现有文件的接线改动

## 从原型迁入的规则

- 先辨认消息方向，再结合前后句检查指代、引用、第三人、否认和身份纠正；截图采集顺序不代表消息时间顺序。
- 称呼原样放在开头，敬语适配已有称呼及可靠关系；不从称呼扩写履历或编造共同经历。
- 区分春节、元旦、元宵、中秋、端午、教师节、国庆、重阳及关系敏感的节日；补充现有生日、纪念日场景。
- 仅在所选场景明确提供时使用年份或生肖；肃穆场景使用克制表达。
- 输出前检查场景、敬语、事实边界、长度及示例信息泄漏。

## 与 Python 原型的适配取舍

| 原型规则 | 当前接入行为及原因 |
| --- | --- |
| 两次独立模型调用 | 合并为一次请求中的判断顺序；沿用 `GenerateAsync` 和原有请求预算 |
| 返回 `name/basis/evidence`，再返回纯文本 | 沿用 `ModelResponse` 的 `address_term/address_evidence/greeting_text` 等字段，不新增中间协议 |
| 自我介绍、唯一关系、正文与备注联合推断、显示名称兜底 | 保留主项目约束：新称呼须来自用户直接称呼对方的正文；附 `chat_message/self`、原文摘录和截图编号 |
| 不确定称呼时停止生成 | 保留主项目的中性祝福回退；人工确认空称呼仍保持为空 |
| 正文 100–200 字 | 保留生成目标 30–80 字、硬上限 120 个可见字符 |
| 默认附 2–4 个微信表情标记 | 保留当次补充要求控制表情；未要求时默认不用，不固定数量 |

这些取舍避免提示词与已有本地校验互相冲突。没有引入 Python、LangChain、Gradio、新 API 配置、新调用阶段或额外重试，也没有改变 App → Core / Windows 的依赖方向。
